# HANDOFF — виповідзення по фабриці (11.09.2026)

> Стан: локально протестовано Yuriy (профіль 503), дозвіл на прод дано 11.09.2026.

## Що зроблено

- **Схема:** `workers.termination_factory_id` (міграція `2026-09-11-termination-factory.sql`). NULL = звільнення з усіх фабрик, як раніше.
- **Сервіс** `endWorkerAtFactory()` у `services/workerFire.ts`: закінчення роботи на ОДНІЙ фабриці. Закриває датою лише умови цієї фабрики (маркер `contracts.data._endedAtFactory` → правило `contract_end` мовчить), прибирає нерозісланий графік цієї фабрики після дати, ставить `worker_factories.valid_to`; з ОСНОВНОЇ — основною стає перша чинна додаткова (журнал `factoryId`, `companyId` — фірма нової основної). Остання фабрика → звичайний `fireWorker`. Журнал `worker_changes`: `factoryEnded` (фабрика → дата), `terminationDate` пише «дата @фабрика».
- **Ланцюжок** `startFactoryEndFlow()` у `services/terminationFlow.ts`: zaświadczenie + wypowiedzenie лише по умовах цієї фабрики (`issueTerminationDocs({factoryId})`); ZUS ZWUA — по фірмі (`contracts.company_id ?? фірма фабрики`), лише якщо чинної умови з тією ж фірмою на інших фабриках не лишилось; ключ `zwua:<worker>:<company>`.
- **API:** `POST /workers/:id/termination {date, factoryId?}`; профіль віддає `terminationFactoryId`. Крон 00:10 `fireDueTerminations` розрізняє обидва режими.
- **Веб:** рядок «Виповідзення» у профілі — селект «усі фабрики / основна / додаткові» + дата + «Зберегти»; бейдж «йде з <фабрика> <дата>». i18n uk/en.
- **Тест:** `services/workerFactoryEnd.integration.test.ts` (два сценарії: з додаткової, з основної).

## Не зроблено / відкрито

- Бот «🔥 Звільнити» — далі звільнення з усіх фабрик (без вибору фабрики).
- Одне заплановане виповідзення на людину (колонка, не таблиця): два різні строки по двох фабриках одночасно поставити не можна — друге перезапише перше.
- Wypowiedzenie генерується в дату виконання (як і при повному звільненні), не в момент подання.
