# Фінансові правила (обовʼязкові)

Доменні правила фінансового блоку. **Прочитай перед будь-якою зміною** у сводних, зарплатах, авансах, фактурах (/cost-invoices, KSeF), банку/касі чи P&L — тут інваріанти, порушення яких уже були інцидентами. Винесено з `CLAUDE.md` (28.08.2026); нові фінансові правила додавай сюди, а не в CLAUDE.md.

Маршрути фінансових роутерів — `docs/API_ROUTES.md`; продакшн — `docs/infrastructure/`.

---

- **Архів фактур на Google Drive** (`services/invoiceArchive.ts`): з 29.09.2026 — **папки офісного акаунта** (office.eurosupp, акаунту Юрія виданий доступ на редагування; id у `settings` `drive_faktury_cost/sales_folder_id`): закупівлі `FAKTURY` → рік → `M<міс>.<рр>` → фірма (папка офісу: ES→`ESG`, Klinex→`KLINEX`, решта по імені без регістру) → KSeF-PDF прямо тут, ручні/скани → підпапка `Skany`, проформи → `Proformy` (пошук підпапок без регістру: в офісі PROFORMA/PROFORMY); продажі `FAKTURY SPRZEDAŻOWI` → `M<міс>.<рр>` → фірма (**без рівня року**, як веде офіс). Кнопка місяця (`drive-month`) = relocate: вже залиті файли звіряються з поточною структурою і переносяться/перейменовуються тим самим id (`?dry=1` — лише план); CLI на проді `node dist/index.mjs archive-invoices --month=YYYY-MM [--dry]`. **імʼя файла = «номер фактури + контрагент»** (`archiveFileName`; закупівлі/скани — постачальник, продажі — покупець), **на Диску лише PDF** (рішення 26.08.2026; legacy-XML перших заливів прибрав разовий `upgradeArchiveNamesV2`, guard у settings). PDF для KSeF — візуалізація з XML (`services/ksefPdf.ts`, за зразком стандартних візуалізацій KSeF: шапка/сторони/позиції/VAT/оплата/QR верифікації; шрифти DejaVu в `assets/fonts/`); сам XML лишається локально в `uploads/ksef-xml/` (термін оплати, хеш QR, регенерація). Скани/ручні — PDF (фото загортається через `imagePdf.ts`); ручна фактура на сайті **не зберігається без файла** (UI-вимога). KSeF API PDF **не віддає** — тільки XML; візуалізацію не «спрощувати» до сирих полів. Рядок без файла на Drive несе `drive_error` і світиться червоним на /cost-invoices — не «лагодити» приховуванням.
- **Журнал змін фактур** (`invoice_audit`, `services/invoiceAudit.ts`): кожен create/patch/file/delete на /cost-invoices і /ksef пише «хто-коли-що» (diff полів old→new, імʼя адміна снапшотом); нова точка мутації фактур МУСИТЬ логувати теж. Веб — модалка «Історія фактури» (іконка 🕘 в рядку).
- **Студент після 26 = повний ZUS** (рішення власника 12.10.2026, кейс Folaranmi): движок (`deriveLegacy`) пропонує з довідки студента статус `zus` групи C без review, коли вік ≥ `studentMaxAge`; до межі — `student` (група B). Раніше довідка після 26 ігнорувалась, статусу з документів не було → порожній статус у сводній, попри зелені осі.
- **Канон полів-двійників** (сторож — `services/dataDrift.ts`: щоденний cron-алерт + лічильник «Потребує уваги»). Вік «до 26» — рахувати з `workers.birth_date` (`isUnder26`), прапорець `under26` — лише фолбек без дати; студент = чекбокс `is_student` АБО `legal_status='student'` (хелпер `stud26Of` в admin-api). Місто фабрики — `factories.city`, далі історія сводних → регіони «Зарплат» (`factoryCityMap`). Снапшоти в `svodni_rows` (city/rate/is_student) — свідомі, не «виправляти». Новий код НЕ читає прапорці напряму.
- **Статус для виплат у рядку сводної — ЗА МІСЯЦЬ рядка** (рішення власника 20.09.2026, кейс Svyrydiuk 08.2026: umowa 11–21.08, сводна формувалась у вересні → «не зголошена»). `services/legalityMonth.ts` — єдиний дозволений міст payroll→движок (нічого не пише): документи перебування/праці — станом на кінець місяця (поточний місяць — на сьогодні), вісь «умова» зелена, якщо підписана umowa перекриває хоч один день місяця (`LegalityInput.window`). Точки: «У сводну» з обліку годин, імпорт/синк сводних, ручне додавання рядка. Порожній снапшот (`legal_status IS NULL`, `legal_source` null або `none`) добирається при повторному «У сводну» для незалочених рядків; заповнений снапшот — не перетирається (як і решта снапшотів).
- **Фабричні правила konto/готівки сводної — у БД, не в коді.** Таблиця `factory_payout_rules` (версії з датою «діє з»; правило діє на сводну МІСЯЦЯ ЦІЛКОМ, у який потрапляє дата): стеля konto-годин (базова/підвищена від порога/лише для фірми), готівковий бонус зл/год, стажевий бонус (сходинки+мін. години), «Premia завжди готівкою». Резолюція — `services/factoryRules.ts` (`PayoutRules.load()` → `.for(factoryId, label, month)`); двигун (`applyLegalDefaults`, `computeSegmented`, `factoryBonusPerHour`) приймає готовий обʼєкт правила (`LegalCtx.rule`). Колишній хардкод (`legacyPayoutRule` у `services/svodni.ts`: стелі DEZYNFEKCJA/SERWIS PLUS/LST 60/70 і Sushi ES 80, бонуси Agram id=12/13 та LST id=1, Premia-cash Agram) — **лише фолбек** для фабрик без збережених версій (сідити БД не можна — id фабрик різняться локально/прод). Нове фабричне правило = версія з сайту (модалка фабрики: перегляд `svodniSensitive`, запис `viewFinance`, після збереження — превʼю/перерахунок незалочених рядків), НЕ нова константа в коді.
- **Фінанси: рапорти мають пріоритет над явками.** Для повних місяців діапазону години пари працівник+фабрика беруться з `monthly_reports` (пропорційне масштабування графікових порцій), без рапорту — із затверджених явок; mtd-порівняння (частковий місяць) — завжди по явках.
- **Фінансові поля — лише для owner** (ставки, рахунки, `viewFinance`/`canFinance`): і в API (фільтрація відповіді), і в UI. Свідомий виняток — cap `factoryRates` (`canFactoryRates`): відкриває **лише ставки в налаштуваннях фабрики** — оплата працівникам (`rate_brutto/rate_netto/night_addon` + `rate/rate_netto` посад) і фактурні (`invoice_rate` фабрики та посад) — для директора міста; привʼязка клієнта до фінблоку (`client_nip`, `pnl_label`) і решта фінансів — як і раніше тільки `viewFinance`.
- **Фінансовий акруал — «місяць мінус 1»:** фактура/зарплата, виставлена чи виплачена в червні за травневу роботу, належить травню (KSeF `revenueMonthFor`, сводні, звірки ЗП банк=M+1). P&L: дохід нетто, собівартість = повна ЗП (брутто+податки+аванси+хостел); сегменти `main`/`cleaning` не змішувати.
- **Жодного матчингу фінансових записів «по сумі».** Евристичний матчинг фактур↔витягів по сумах був відкинутий власником. Дозволено: точний номер фактури або її KSeF-номер у назві переказу (22.10.2026: адміністратори вспульнот пишуть «<KSeF>… B7_9_2026» — номер із «_» сам по собі НЕ якір), повна коректа продажу того самого покупця — лише однозначна пара (`matchKsefPayments`), токени імені (звірка ЗП — строгий прохід, потім fuzzy з авто-підтвердженням лише коли сума сходиться ±2 zł, решта — ручне підтвердження у `payroll_name_matches`).
- **Парсери сводних/KSeF — під тестами** (`services/*.test.ts`): формати таблиць гуляють між містами й місяцями; змінюєш парсер — додай/онови фікстуру. Тест-скрипт використовує `test-hooks.mjs` (безрозширенні імпорти під raw Node) і фейковий `DATABASE_URL`.
- **Księgowe години НІКОЛИ не більші за відпрацьовані** (рішення власника 22.10.2026, кейс Kuanyshbek: «усе на конто» при нетто 31,40 > księg. 25,35 вигадало 45 год і 1 424 zł брутто). Єдине місце — `finish()` у `applyLegalDefaults` (`services/svodni.ts`), ним же йдуть сегменти й батько з побажанням. Оподаткована пара: конто ≤ відпрацьовані × księg. нетто — надлишок (нетто понад 25,35, премія, фабрична надбавка) іде готівкою, і при «усе на конто» / «N год» / «сума» теж; брутто понад години не вигадуємо (власник його не знає). Неоподаткована (студент, нетто = брутто): усе на конто, як і раніше, обрізаються лише години; księg. brutto = конто разом із премією — це не «розрив пари» (`serializeRow` не підсвічує). Порізаний рядок із побажанням — стеля Σ по сегментах (`ctx.kontoHoursCap`), бо ставка батька усереднена. Статус «polak» за документами (громадянство PL/ЄС) студентства з профілю не знімає — `studentForStatus`/`manualStudent` у `services/effectiveStatus.ts`; новий вивід «студент зі статусу» — лише через них.
- **Години в повідомленні — ПО ФАБРИЦІ** (рішення власника 15.10.2026; `services/notifyHours.ts` — єдиний резолвер): ліміт konto рядка сводної = години людини на ФАБРИЦІ рядка — `worker_notify_hours` (manual — вписано вручну в профілі/сводній/імпорті; powiadomienie — з документа Powiadomienie UA), без рядка — старе спільне `workers.notify_hours` (ручне). У форму повідомлення години йдуть ЛИШЕ з налаштувань фабрики (`factories.ua_notify_hours`, стандарт 40 год/міс, Налаштування → praca.gov.pl → Фабрики; перед подачею правляться вручну), з профілю — ні. Після подачі (робот) або вписання годин у ручну форму документа `applyNotificationHours` пише рядок фабрики, лише якщо для неї нема ручного значення (ні свого manual, ні спільного), журнал `worker_changes` з `factory_id` (adminId NULL), незалочені рядки сводної цієї фабрики — одразу (`autoApplyNotifyChange`), залочені — у ревʼю при розлоку. Зміна профілю з превʼю: `{notifyHours, notifyHoursFactoryId}` → двигун зачіпає лише рядки цієї фабрики. Нова поверхня, що формує рядок сводної, бере `resolveNotifyHours(legacy, byFactory, factoryId)`, не голе `workers.notify_hours`. У секції 4 форми «umowa o pracę» порожнє в фірмі = 0 (у нас лише zlecenie).
