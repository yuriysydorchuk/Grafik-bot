# Задача: powiadomienie UA — роботодавці з умов і явок, не лише з профілю (#44)

- **Статус:** 🔲 заплановано (план на узгодження, рішення власника 13.11.2026: «підготов план»)
- **Дата:** 2026-11-13
- **Автор/сесія:** Claude (тріаж зголошень 13.11)

## Мета

Обовʼязок powiadomienie (і задачі UA ступенів 1–2) має виникати по КОЖНІЙ фірмі, на яку людина реально
працює, а не лише по фірмах з профілю. Готово, коли: людина з явками/підписаною умовою на фабриці фірми X без
powiadomienia для X отримує обовʼязок і задачу з правильним строком (7 днів від першої явки на X), а документ
для X закриває лише його.

## Контекст

`legalityRecompute.ts loadWorkerEmployers`: роботодавці = основна фабрика + чинні `worker_factories`. Явки на
інших фабриках (`scheduleFactoriesOf`) дають лише попередження `schedule_outside_factories`. Строк одного
обовʼязку на всі фірми — `employerSince` (перший робочий день взагалі). На проді 14 з 15 пар «активний ×
фабрика з явками поза профілем» без рядка в профілі; серед українців — 8 пар (7 людей) з фірмами поза профілем,
4 з них без powiadomienia для тієї фірми → ~4 нові задачі одразу (оцінка 13.11, read-only).

Зачіпає: движок легальності (високий ризик), автозадачі UA, профіль (слот Powiadomienie по роботодавцях).

## План

1. **Роботодавці = профіль ∪ умови ∪ явки.** `loadWorkerEmployers` додає: (а) фірми підписаних умов
   (`contracts.status in (worker_signed, signed)`, не подієві kind, `date_to` ≥ сьогодні − 30 дн.),
   (б) фірми фабрик з явками `present` за останні 90 днів (`scheduleFactoriesOf` розширити датою першої явки).
   Прапорець `source: profile|contract|shift` у `LegalityEmployer` — для профілю й причин.
2. **Строк по фірмі.** `LegalityEmployer.since` = перша явка `present` на фабриках фірми (затверджений або
   розісланий тиждень, як у `firstWorkDate`) → `contracts.date_from` → `employerSince`. У движку `dueAt` для
   обовʼязку фірми = `since + days`; «повернений після звільнення» — лише дати після повернення (як зараз).
3. **UA-задачі.** `uaNotification` бере `start` з обовʼязку фірми (вже є `params`), `uaAttended` — явки на
   фабриках цієї фірми. Legacy-гейт (`legacyBefore`) лишається: старі прострочені обовʼязки задач не створюють
   — тому 4 нові задачі зʼявляться лише для строків після дати запуску модуля (перевірити на дампі).
4. **Документи.** `employerOk` без змін: powiadomienie для фірми закриває лише її обовʼязок; документ на фірму з
   нового списку перестає бути `mismatch` (стає `other`) — менше хибних review.
5. **Профіль.** Слот Powiadomienie «по роботодавцях» показує і нові фірми з позначкою джерела («з явок»,
   «з умови»), щоб офіс бачив, звідки взявся обовʼязок.
6. **Перевірка перед деплоєм.** На нічному дампі проду: порахувати людей, у яких зміниться статус/обовʼязки;
   список нових задач (очікувано ≤ 5) — показати власнику; переконатись, що жоден `legal` не стає `illegal`
   лише через новий обовʼязок (`hard=false` у правила — лише попередження).
7. Тести: юніт движка (фірма з явок без документа → обовʼязок із правильним dueAt; документ на цю фірму
   закриває; подієва умова не створює роботодавця), інтеграційний UA-синк (задача по новій фірмі).

## Ризики

- Явка на «чужій» фабриці за помилкою графіку створить обовʼязок → джерело видно в профілі, обовʼязок зникає,
  коли явку виправлено (кеш перераховується).
- Фірми з різних умов у межах 30 днів після закінчення — обовʼязок ще висить; після 30 днів зникає.
