# Фінансова звірка — виконуваний чеклист

Звірка = знайти й пояснити розбіжність, **не** виправити її. Правки даних — лише після явного підтвердження користувача поіменним списком змін.

## Незмінні правила (порушення = регресія)

1. **Нічого не правимо в даних без явного «так».** Фіксимо код/парсер, якщо помилка в ньому; дані — тільки за підтвердженням.
2. **Жодного матчингу «по сумі».** Дозволено: точний номер фактури в назві переказу; токени імені для ЗП (строгий прохід → fuzzy з авто-підтвердженням лише при збігу суми ±2 zł, решта — вручну в `payroll_name_matches`).
3. **Акруал «місяць −1»:** фактура/ЗП, виставлена чи виплачена в M за роботу M−1, належить M−1 (KSeF `revenueMonthFor`, сводні; звірка ЗП: банк = M+1).
4. **Рапорти > явки:** для повних місяців години пари працівник+фабрика — з `monthly_reports` (пропорційне масштабування графікових порцій); без рапорту — затверджені явки; частковий місяць (mtd) — завжди явки.
5. **Дати — рядками** (`YYYY-MM-DD`), тижні беруться з запасом (`weekFromForMonth`, −6 днів) і кожна зміна фільтрується за `entryDateStr`. Ніяких `toISOString` для дат.
6. **P&L:** дохід нетто; собівартість = повна ЗП (брутто + податки + аванси + хостел); сегменти `main`/`cleaning` не змішувати. Закупівлі KSeF (Subject2) — довідкові, у P&L не йдуть.
7. **Звіряємо до злотого:** розбіжність ≤ 0.01 zł = збіг; більша — мусить мати назване пояснення (не «приблизно зійшлося»).

## Порядок звірки місяця M

Інструмент — scratch-скрипти за скілом `scratch-db` (read-only). Порівнюй **сирі клітинки** джерела проти сайту, без довиведень з обох боків одночасно.

1. **Межі:** зафіксуй M; пам'ятай, що виплати/фактури за M фізично живуть у M+1.
2. **Години:** книга годин (вкладки Google-таблиць, `readSourceGrids`) vs `monthly_reports` vs явки. Вкладки-сміття (`GODZIN MIES`, `MAILE`, `WORK LIST`, `OFFICE/ОФИС`) — скіп.
3. **Сводні:** `svodni_rows` (site) vs księg-блоки/готівкові книги таблиці (book), по фабриці й людині. Пам'ятай: агрегати — `segment_of IS NULL`; бонуси Agram/LST (`agramBonusPerHour`) і резолюція ставок (`resolveBaseRates`) — імпортом із `services/svodni.ts`; студент до 26 — нетто = брутто, без бонусів; залочені рядки (`svodni_locks`) не чіпаються, `staleLocks` — сигнал користувачу.
4. **Зарплати:** payroll (зведені) vs банківські перекази M+1 vs готівка каси. Матч — за правилом 2.
5. **Дохід:** KSeF sale (акруал M−1, матч покупця по NIP `factories.client_nip`) vs P&L revenue vs надходження на рахунки.
6. **Банк/каса:** `bank_transactions` за категоріями vs `cash_entries`; рівняння звірки — `GET /cashflow`. Кредитний рахунок `PL75…8415` — поза операційною касою. Класифікація: bucket-и в `services/bankClassify.ts`, категорії — БД `expense_categories` (patterns: Postgres `\y`, не `\b`).

## Результат звірки

Компактний звіт користувачу: що зійшлося (сума, до злотого), що ні — таблиця «джерело / сайт / diff / пояснення». Для кожної розбіжності — діагноз: помилка парсера (→ фікс коду + фікстура в `services/*.test.ts`), помилка даних (→ список правок на підтвердження), або законна різниця (пояснити правилом вище).
