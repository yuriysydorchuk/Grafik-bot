# HANDOFF: ревʼю змін при розблокуванні сводної + «Діє з» для посади/дати народження (14.08.2026)

Тимчасова записка сесії. Довговічні факти вже в `PROJECT_MAP.md` (розділ «Сводні → Зміни профілю з датою набуття / Ревʼю при розблокуванні»).

## Що зроблено (4 запити власника)

1. **Посада питає «від коли».** `ProfileChangeModal` («Діє з + превʼю») винесено у спільний
   `web/src/components/ProfileChangeModal.tsx`; `WorkerModal` (редагування зі списку і з профілю)
   тепер перехоплює свод-релевантні поля — посаду, ставку брутто, студента: решта полів
   зберігається звичайним PATCH, ці — через превʼю впливу на сводні (cap `svodni`; без капи — як досі).
2. **Фікс stud26-бага.** Дата народження йде через ту саму модалку превʼю → рядки сводної
   перераховуються одразу (нетто = брутто, все на конто), без ритуалу «пересейвити статус студента».
   **Дату набуття для дати народження модалка НЕ питає** (фідбек власника: це факт) — from = сама
   дата народження (очищення — рання константа), діє по всіх місяцях. Очищення дати скидає `under26`
   в обох шляхах (PATCH + normTrackedChanges).
3. **Попередження про лок.** Банер у модалці: «N рядків у затверджених сводних зараз НЕ зміняться;
   при розблокуванні система запропонує прийняти або відхилити».
4. **Побажання по виплаті — одне підтвердження (докат 14.08 увечері).** Вибір типу з сумою
   («Сума/N годин на конто») більше не відкриває модалку одразу: спершу вводиться сума
   (підказка біля поля), тоді тип+сума йдуть ОДНІЄЮ зміною → одна модалка «від коли».
   Порожня сума при розфокусі = скасування вибору. Пізніша правка лише суми — одна модалка,
   як і було. `PayoutPrefRow` у `WorkerDetail.tsx`; бекенд без змін.
5. **Ревʼю при розблокуванні.** `POST /svodni/lock-pending` (список змін журналу після `lockedAt`,
   критерій = staleLocks, з превʼю дифів по області) + `applyChangeIds` в unlock-гілці
   `POST /svodni/lock`. Веб: «Розблокувати» → модалка ревʼю (прийняти/відхилити кожну;
   «Скасувати» = лок лишається). Прийняти = привести рядки області до ПОТОЧНОГО профілю по полю.
   Схема БД не мінялась — усе на наявному `worker_changes` (`appliedRows`/`skippedLocked`).

## Нюанси / підводні камені

- **Батч фактур 12.08 (Drive-архів KSeF) свідомо НЕ закомічений і НЕ задеплоєний** — чекає тесту
  власника. Коміт цього батчу вибірковий; у спільних файлах (`web/src/lib/i18n.tsx`,
  `PROJECT_MAP.md`) разом поїхали інертні словникові ключі/док-абзаци батчу фактур — код їх не
  використовує, поки той батч не задеплоєний.
- «Прийняти» в ревʼю застосовує **поточне** значення профілю (кілька змін одного поля колапсують).
- Відхилена зміна не вертається у наступному циклі лок→розлок (критерій — createdAt > нового lockedAt).
  АЛЕ: `freezeUnder26AtLock` при повторному локу все одно перерахує вік з поточної дати народження —
  це давнє свідоме правило («вік на дату виплати»), відхилення birthDate-зміни його не скасовує.
- Зміни, зроблені під локом голим PATCH з effective=сьогодні, у ревʼю минулого місяця не потраплять
  (effectiveDate поза місяцем) — консистентно з ❗ staleLocks. birthDate тепер завжди потрапляє
  (effective = дата народження).
